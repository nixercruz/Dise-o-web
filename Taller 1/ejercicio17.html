Guía para identificar requisitos funcionales y no funcionales

En esta guía aprenderás a reconocer qué debe hacer un sistema y qué condiciones debe cumplir antes de comenzar a desarrollarlo.

1. ¿Qué son los requisitos?

Los requisitos describen las necesidades y expectativas de las personas que utilizarán un sistema. Sirven como guía para planear, construir y comprobar que el software resuelva el problema correcto.

Antes de escribir requisitos, identifica qué problema se quiere solucionar, quién utilizará el sistema y qué resultado espera obtener.

2. ¿Cómo obtener los requisitos?

Puedes seguir estos pasos para comprender la necesidad del usuario y convertirla en requisitos claros:

  1. Identifica a los interesados: pregunta quién utilizará el sistema y quién se verá afectado por él.
  2. Comprende el problema: conversa con los usuarios sobre las dificultades que tienen y lo que necesitan mejorar.
  3. Recopila información: realiza entrevistas, encuestas, observación o revisa los documentos y procesos actuales.
  4. Organiza las necesidades: separa las funciones que debe realizar el sistema de las condiciones de calidad que debe cumplir.
  5. Redacta y valida: escribe cada requisito de forma clara, verifica que sea posible comprobarlo y confirma con el usuario que sea correcto.

Consejo: evita suponer lo que necesita el usuario. Pregunta, toma apuntes y confirma tus conclusiones antes de continuar.

3. Requisitos funcionales

Indican qué debe hacer el sistema. Describen funciones, acciones o servicios que estarán disponibles para los usuarios.

Ejemplo: sistema para una biblioteca

  • El sistema debe permitir registrar nuevos libros.
  • El sistema debe permitir buscar libros por título o autor.
  • El sistema debe registrar el préstamo de un libro a un aprendiz.
  • El sistema debe mostrar la fecha de devolución de cada préstamo.

Una forma útil de redactarlos es: “El sistema debe permitir que [usuario] realice [acción]”.

4. Requisitos no funcionales

Describen cómo debe funcionar el sistema o qué características de calidad y restricciones debe cumplir. No se enfocan en una función específica, sino en las condiciones del servicio.

Ejemplo: sistema para una biblioteca

  • Rendimiento: los resultados de una búsqueda deben mostrarse en máximo 3 segundos bajo las condiciones acordadas.
  • Seguridad: las contraseñas deben almacenarse de forma segura y no como texto visible.
  • Usabilidad: las opciones principales deben tener nombres claros y ser fáciles de encontrar.
  • Disponibilidad: el sistema debe estar disponible durante el horario de atención definido por la biblioteca.

Procura que estos requisitos sean medibles. Por ejemplo, “debe ser rápido” es muy general; “debe responder en máximo 3 segundos” se puede comprobar.

5. ¿Cómo distinguirlos?

Hazte esta pregunta: ¿describe una acción que el sistema realiza o una condición de calidad?

  • “Registrar un préstamo” es un requisito funcional porque describe una acción del sistema.
  • “Mostrar la pantalla en menos de 2 segundos” es un requisito no funcional porque establece una condición de rendimiento.

Plantilla para tus apuntes

Al entrevistar a un usuario, puedes organizar la información así:

  • Necesidad: ¿qué problema tiene?
  • Usuario: ¿quién necesita la solución?
  • Requisito funcional: ¿qué acción debe permitir el sistema?
  • Requisito no funcional: ¿con qué nivel de calidad o bajo qué condición debe realizarse?
  • Validación: ¿cómo comprobarás que se cumple?

6. Revisa tus requisitos antes de entregarlos

  1. ¿Cada requisito se entiende sin explicaciones adicionales?
  2. ¿Está relacionado con una necesidad real del usuario?
  3. ¿No mezcla varias necesidades en una sola frase?
  4. ¿Se puede comprobar o validar?
  5. ¿El usuario confirmó que representa lo que necesita?
